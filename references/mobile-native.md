# 移动端原生 App 界面

用途：设计或评审 iOS、Android 原生 App（含 React Native、Flutter、SwiftUI、Jetpack Compose）时使用。移动端网页见 accessibility-states-motion.md 的响应式部分。原生 App 首先遵守所在平台的习惯，其次才是品牌个性；以下是两大平台指南中最常用的约定，具体数值以当前官方文档为准。

## 平台差异速查

| 项目 | iOS（Human Interface Guidelines） | Android（Material Design 3） |
| --- | --- | --- |
| 尺寸单位 | pt | dp（文字用 sp） |
| 最小触控目标 | 44×44 pt | 48×48 dp |
| 主导航 | 底部标签栏，最多 5 项 | 底部导航栏 3–5 项；大屏用导航栏或抽屉 |
| 返回 | 左上返回按钮 + 从左边缘右滑 | 系统返回手势或按键；顶栏返回箭头 |
| 主要操作 | 导航栏右侧按钮或页面内按钮 | 悬浮操作按钮（FAB）或页面内按钮 |
| 系统字体 | San Francisco；中文为苹方 | Roboto；中文为 Noto Sans CJK 或厂商字体 |
| 字号随系统设置 | Dynamic Type | 字体缩放（sp） |
| 弹层 | 底部弹层（sheet）、操作列表 | 底部弹层、对话框 |
| 层级表达 | 模糊材质、分隔线、轻阴影 | 色调层级（表面颜色变化）与阴影 |

跨平台框架也应按平台切换这些行为，不要把一个平台的导航和控件原样搬到另一个平台。

## 布局

- **安全区**：内容避开刘海、灵动岛、状态栏、底部手势条和圆角。背景可以延伸到屏幕边缘，可交互内容留在安全区内。
- **拇指可达**：高频操作放在屏幕下半部；顶部角落留给不常用或需要谨慎的操作。
- **边距**：左右边距常用 16（pt/dp），列表项内的文字与图标对齐到同一条线。
- **一屏一件事**：每个页面有一个清楚的主任务；复杂流程拆成多步而不是塞进一页。
- **屏幕尺寸**：从小屏手机到大屏、折叠屏和平板都要可用；平板不要只是把手机界面拉宽，可改为分栏。
- **横屏与键盘**：输入框获得焦点时不被键盘遮住，提交按钮保持可见或可滚动到达。

## 导航与手势

- 底部标签用于同级的主要栏目，切换时保留各栏目自己的浏览位置；不把一次性动作（如“发布”）之外的操作做成标签。
- 层级导航（进入详情）与模态呈现（完成一件独立任务，如新建、编辑）区分使用；模态页面有明确的“取消”和“完成”。
- 不覆盖或阻断系统手势（边缘返回、底部上滑回主屏）。自定义手势必须有可见的按钮替代。
- 长按、滑动删除等隐藏操作要有其他可发现的入口。

## 控件与反馈

- 优先使用平台原生控件（开关、选择器、日期选择、分段控件），用户已经知道怎么用，也自带可访问性支持。
- 按下要有即时反馈（高亮、涟漪）；适度使用触感反馈确认关键操作，不滥用。
- 加载：内容区用骨架或占位，列表支持下拉刷新；按钮提交时显示进行中并防止重复点击。
- 离线与弱网是常态：显示缓存内容并标明时效，操作失败时保留输入并允许重试。
- 权限（通知、相机、定位）在用到时再请求，并先用一句话说明用途；被拒绝后功能可降级且提供去设置的入口。
- 表单：选择合适的键盘类型（数字、邮箱、电话），支持自动填充；减少输入，能选不填。

## 文字与可访问性

- 使用平台的文字样式层级并支持系统字号放大：放大到最大档时布局可换行、可滚动，不截断关键信息。正文 iOS 默认 17pt，Android 常用 14–16sp。
- 对比度要求与网页相同（正文 4.5:1，大字与非文本 3:1），在强光下使用的场景建议留更多余量。
- 每个可交互元素都有读屏标签（VoiceOver、TalkBack）；图标按钮必须有文字标签；读屏顺序符合视觉顺序。
- 支持暗色模式（见 dark-mode.md）和“减少动态效果”系统设置。
- 中文排版规则见 chinese-typography.md。

## 检查

1. 在最小和最大的目标机型、亮/暗主题、最大系统字号下各看一遍主要页面。
2. 单手操作一遍主任务，记录够不着或容易误触的地方。
3. 打开读屏走一遍主任务。
4. 断网、弱网、权限被拒、键盘弹出、来电打断后返回，这些情况下界面是否仍然正常。
5. 平台习惯是否正确：返回方式、导航位置、弹层样式、系统控件。

国内小程序（微信、支付宝、小红书等）另有各自的平台设计规范与审核要求，按对应官方文档执行，本文不覆盖。
